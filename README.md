# Агент проверки требований

Агент для BCC-HUB x MNU FinTech Hackathon. Он проводит статическое ревью документа с требованиями (PDF, DOCX, MD, TXT) по ISO/IEC/IEEE 29148:2018 (п. 5.2.5–5.2.6) и IEEE 830-1998 (п. 4.3). На выходе агент выдаёт отчёт на русском языке в трёх форматах: Markdown, наглядный HTML и JSON. Агент формулирует уточняющие вопросы заказчику, а в режиме `-i` задаёт их в терминале и учитывает ответы в итоговом заключении. Ещё он может посчитать собственную полноту и точность по эталонному списку дефектов.

## Результат

Проверено на документе организаторов «Уведомление о расходах по карте» (`docs/requirements.md`; итоговый прогон сделан по requirements.md, остальные строки по его PDF-версии) против эталона из 22 дефектов, составленного вручную (`gold/defects.md`).

| Конфигурация | Полнота | Точность | Время |
| :- | :- | :- | :- |
| **Итоговый прогон 0.8.0 по docs/requirements.md** (ансамбль, `reports/report.md`) | **19/22 (86%)** | **67%** (22 из 33) | ~15 мин |
| Ансамбль, 5 прогонов версии 0.8.1 по docs/requirements.md | от 14 до 19 из 22, в среднем 17 (77%) | 44–85% | ~15 мин |
| **Ансамбль Cerebras gpt-oss-120b + Gemini 3.5 flash-lite**, версия 0.7, по PDF | **в среднем 86%** (3 прогона: 18, 22, 17 из 22); лучший прогон **22/22** | 40–51% | 15–16 мин |
| Cerebras gpt-oss-120b, одна модель | 82% (18/22) | 44% | 13 мин |
| Gemini 3.5 flash-lite, одна модель | 73% (16/22) | 88% | 2 мин |

Результат одного запуска заметно гуляет: модели от прогона к прогону находят разное, а при лимитах (429) агент переключается на запасную модель. Поэтому мы показываем все прогоны, а не только лучший. Точность здесь означает долю замечаний, совпавших с эталоном. Остальные замечания не обязательно ложные: эталон неполон. Полная таблица и разбор — в [`reports/comparison.md`](reports/comparison.md).

- Итоговый отчёт агента: [`reports/report.md`](reports/report.md), наглядная версия `reports/report.html`, данные `reports/report.json`, сверка с эталоном `reports/report_eval.md`.
- Все прогоны для сравнения моделей лежат в `reports/runs/` (каждый отчёт сгенерирован агентом, вручную не правился).

## Быстрый старт

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env                # macOS/Linux: cp .env.example .env
# впишите ключи в .env (см. ниже)
python -m validator docs/requirements.md -o reports/report.md
```

Отчёт появится в `reports/report.md`, рядом лягут `reports/report.html` и `reports/report.json`. Вход: PDF, DOCX, MD или TXT, любой документ с требованиями, а не только документ организаторов. Если файл повреждён, пустой (например, скан без текстового слоя) или в неподдерживаемом формате, агент не падает, а записывает в тот же путь отчёт-диагностику с причиной и советом, что сделать, и завершается с кодом 2.

Одной командой со сверкой по эталону: `run.bat` на Windows или `./run.sh` на macOS и Linux (по умолчанию берут `docs/requirements.md`, можно передать свой файл).

Нужен Python 3.10 или новее.

## Ключи LLM

Хватит одного бесплатного ключа, но лучший результат даёт ансамбль из двух.

1. **Cerebras** (основная модель `gpt-oss-120b`): https://cloud.cerebras.ai/ → API Keys. Вставьте в `.env` строку `CEREBRAS_API_KEY=...`.
2. **Google AI Studio** (вторая модель ансамбля и запасные): https://aistudio.google.com/ → Get API key. Вставьте `GEMINI_API_KEY=...`.

Модели задаются в `.env`:

| Переменная | По умолчанию | Смысл |
| :- | :- | :- |
| `GEMINI_MODEL` | `cerebras:gpt-oss-120b` | основная модель; префикс `cerebras:`, `openrouter:`, `groq:`, `openai:` — OpenAI-совместимый API, без префикса — Gemini |
| `GEMINI_FALLBACK_MODELS` | `gemini-3.8-flash,gemini-3.5-flash,gemini-3.5-flash-lite` | запасные модели по порядку |
| `ENSEMBLE_MODELS` | `gemini-3.5-flash-lite` | вторая модель ансамбля; пусто — одна модель |

Если есть только ключ Gemini, поставьте `GEMINI_MODEL=gemini-3.8-flash` и оставьте `ENSEMBLE_MODELS` пустым. Модель без ключа (или с заглушкой `your_..._here` из `.env.example`) агент пропускает с предупреждением; модель, чей ключ провайдер отклонил (401/403), выбывает из цепочки, и прогон идёт на следующей. При ошибках 429 и 503 он повторяет запрос с паузой и переходит на запасную модель. Модели, которые реально ответили, записываются в паспорт прогона.

Новые ключи AI Studio (начинаются с `AQ.`) работают только с `google-genai` 3.6 и новее. При ошибке 401 выполните `pip install -U -r requirements.txt`.

Файл `.env` в git не попадает, ключей в репозитории нет.

## Параметры

| Флаг | Что делает |
| :--- | :--- |
| `-o путь.md` | куда записать отчёт (рядом появятся `.html` и `.json`) |
| `-i` | интерактивный режим: агент задаёт заказчику уточняющие вопросы и учитывает ответы в итоговом заключении |
| `--gold gold/defects.md` | сверить замечания агента с эталоном и посчитать полноту (`report_eval.md`) |
| `--model` | переопределить основную модель из `.env` (например `cerebras:gpt-oss-120b`) |
| `--ensemble` | модели ансамбля через запятую, иначе `ENSEMBLE_MODELS` из `.env` |
| `--no-critic` | отключить шаг критика (для сравнения качества) |
| `--no-lenses` | отключить целевые проходы-чеклисты (быстрее, но полнота ниже) |
| `--eco` / `--full` | экономный (~14 запросов) или полный (~28) режим; по умолчанию полный для Cerebras и lite-моделей, экономный для остальных |
| `--no-cache` | не использовать кэш ответов модели |

## Архитектура

```
документ (PDF/DOCX/MD)
  │ 1. Загрузчик: текст с номерами страниц и строк                 [код]
  │ 2. Нарезчик: отдельные требования с дословными цитатами        [LLM]
  │ 3. Правила: размытые слова, пустые разделы, прочерки, TBD      [код]
  │ 4. Аналитик требований: 9 свойств ISO 29148 для каждого        [LLM, пачками]
  │ 5. Аналитик набора: противоречия, пропуски, части A↔B,
  │    трассировка требований на критерии приёмки                  [LLM]
  │    Шаги 4–5b ансамбль делает двумя моделями параллельно,
  │    замечания объединяются                                      [LLM×2]
  │ 5b. 8 целевых проходов-чеклистов (3 группы): контракт API,
  │    данные и единицы, дата/время, негативные сценарии, область
  │    и термины, ИБ и ПДн, эксплуатация, согласованность частей [LLM]
  │ 6. Верификатор: цитата замечания должна быть в документе
  │    (точно или с допуском на мелкие искажения)                [код]
  │ 6b. Слияние дублей: замечания об одном дефекте из разных
  │    проходов объединяются, все места сохраняются              [LLM]
  │ 7. Критик: второй ревьюер отсеивает ложные замечания;
  │    важные отклонения перепроверяются: без цитаты-основания
  │    замечание возвращается в отчёт
  │    и калибрует критичность                                     [LLM]
  │ 8. Уточнения: вопросы заказчику, в режиме -i ответы
  │    учитываются в итоге                                         [человек]
  │ 9. Итог: готовность к разработке и тестированию, приоритеты    [LLM]
  ▼
report.md · report.html · report.json · report_eval.md
```

Принципы:
- **Гибридная проверка.** Дешёвые и надёжные проверки делает код, смысловой анализ делает модель.
- **Защита от галлюцинаций.** Модель отвечает строго по JSON-схемам (pydantic). Каждая цитата проверяется по тексту документа. Отклонённые замечания не скрываются, а выносятся в приложение отчёта.
- **Ссылка на место.** Каждое замечание ссылается на строку документа (для PDF ещё и на страницу).
- **Устойчивость.** При ошибках 429 и 5xx агент повторяет запрос с нарастающей паузой и переходит на запасную модель. Если перегружены все модели, он делает паузу и проходит цепочку заново (до 3 кругов). Прерванный прогон можно просто запустить снова: готовые шаги возьмутся из кэша. В паспорт прогона попадает модель, которая реально отвечала.
- **Защита нарезки.** Если модель вернула пустой или слишком короткий список требований (меньше 40% от кандидатов, найденных кодом), агент повторяет запрос мимо кэша, затем переключается на следующую модель, а в крайнем случае режет документ кодом по пунктам, нумерации, строкам таблиц и разделам (`validator/segment_rules.py`). С пустым списком прогон дальше не идёт. Требования, чьей цитаты нет в документе, отбрасываются.
- **Нарезка модель + код (0.5.2).** Даже когда модель нарезала достаточно, агент добавляет кандидатов из нарезки кодом, которых нет ни в одном требовании модели (≥60% слов не совпадает): так не теряются разделы вроде URL, тестирования, UI и диаграмм. В паспорте видно, сколько добавлено.
- **Критик под контролем (0.5.2).** Находки, подтверждённые правилом (в том числе слитые с замечанием модели), критику не отдаются. Каждое отклонение критика перепроверяется: оно остаётся, только если найдена дословная цитата-основание.
- **Экономный режим (0.6, по умолчанию).** Весь прогон около 12–13 запросов к модели: нарезка, 3 пакета проверки требований, проверка набора, 3 группы целевых проходов, слияние дублей, критик, перепроверка, итог (+1 на сверку с эталоном). Так прогон помещается в бесплатный дневной лимит gemini-3.5-flash (20 запросов). Если модель в большом пакете пропустила требования, делается один дозапрос. Флаг `--full` включает прежний режим: пакеты по 6 и каждый проход отдельно (20+ запросов).
- **Общие проверки (0.6).** Добавлен проход «Область применения, термины и граничные значения»: валюты и статусы объектов, настройка при выключенной функции, неоднозначные термины, от которых зависит расчёт, граничные суммы. В проход негативных сценариев добавлены конфликт «не чаще N раз» с правилами повторного срабатывания и идемпотентность (ключ, окно). Пункты общие для финтех-ТЗ и не пересказывают эталон.
- **Адаптивный бюджет (0.7).** Режим выбирается по модели, которая реально отвечает после нарезки. Для flash работает экономный режим (около 14 запросов, помещается в дневной лимит 20). Облегчённая lite-модель с более высоким лимитом получает полный режим: пакеты по 6 требований, каждый из 8 проходов отдельно, сценарии по каждому ФТ отдельно (около 28 запросов): узкий фокус ей помогает. Режим можно задать явно: `--eco` или `--full`.
- **Прогон сценариев по ФТ (0.7).** Для каждого функционального требования модель как тестировщик пошагово исполняет правила документа на критериях приёмки и типовых граничных случаях. Среди них: значение на границе, одна большая операция, смена настройки в середине периода, выключение и включение, возврат после срабатывания, граница периода, другая валюта или статус, повтор события. Дефект — шаг, где документ молчит, двусмыслен или два места дают разный результат. Сценарии общие и в `validator/criteria.py` (SCENARIOS).
- **Ансамбль моделей (0.7).** Разные модели находят разные дефекты: в отдельных прогонах Cerebras, OpenRouter и Gemini вместе покрыли все 22 эталонных. Поэтому вторая модель проверяет те же требования параллельно, слияние дублей объединяет замечания, а дефект, найденный независимо двумя моделями, критик не снимает. Сбой второй модели не роняет прогон.
- **Чистые формулировки (0.8).** Поле «критерий» приводится кодом к свойству ISO 29148 или названию прохода, поэтому служебный текст промптов не попадает в отчёт.
- **Честная верификация (0.8.1).** Служебный префикс списка требований («R-51 (без номера, раздел, тип): …»), который модель иногда копирует в цитату, снимается до проверки: раньше из-за него отбрасывались верные замечания. Отклонение критика не принимается, если его «цитата-основание» указывает на то же место, что и само замечание.
- **Воспроизводимость.** Ответы модели кэшируются в `.cache/`, поэтому повторный прогон даёт тот же результат и не тратит лимит. В паспорте прогона указаны модель и версия агента (git-коммит).
- **Измеримое качество.** `validator.evaluate` считает полноту по эталону `gold/defects.md`.

## Веб-оболочка для демо

```bash
python -m validator.web
```

Откроется http://127.0.0.1:8000. Там можно загрузить документ, следить за шагами и открыть HTML-отчёт. Оболочка работает только на этом компьютере, внутри тот же агент. Отчёты сохраняются в `reports/web/`.

## Сравнение моделей

```bash
python -m validator docs/requirements.md -o reports/runs/strong/report.md --model <другая модель> --gold gold/defects.md
```

Кэш разделён по основной модели, поэтому ответы разных моделей не смешиваются.

## Оценка качества

```bash
python -m validator.evaluate reports/report.json gold/defects.md -o reports/eval.md
```

## Офлайн-тест (без ключа)

```bash
python -m unittest discover -s tests
```

## Структура

| Файл | Что делает |
| :--- | :--- |
| `validator/loader.py` | чтение PDF, DOCX, MD |
| `validator/rules.py` | детерминированные правила |
| `validator/segment_rules.py` | запасная нарезка требований кодом |
| `validator/criteria.py` | критерии 29148 и 830 |
| `validator/pipeline.py` | шаги агента и промпты |
| `validator/verify.py` | проверка цитат, поиск места в документе |
| `validator/report.py` | отчёт Markdown и JSON |
| `validator/html_report.py` | наглядный HTML-отчёт |
| `validator/evaluate.py` | оценка против эталона |
| `validator/web.py` | локальная веб-оболочка для демо |
| `validator/llm.py` | клиент LLM: Gemini и OpenAI-совместимые (Cerebras, OpenRouter, Groq), ансамбль, кэш, повторы и запасные модели |
| `gold/defects.md` | эталонный список дефектов |
| `docs/requirements.md` | проверяемый документ организаторов (`requirements.pdf` — его PDF-версия) |
| `reports/` | итоговый отчёт, сравнение моделей, все прогоны в `runs/` |

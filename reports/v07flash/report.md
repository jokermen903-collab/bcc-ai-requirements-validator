> Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.

- **F-8 [существенный] Полнота** (стр. 1, строка 39; модель): «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.»  
  Проблема: В требовании к данным не указаны типы данных, обязательность полей и ограничения длины для каждого атрибута, что не позволяет разработчику корректно спроектировать таблицу в БД.  
  Исправить: Дополнить требование типами данных и ограничениями для каждого перечисляемого атрибута в соответствии с моделью данных.  
  Вопрос: Какие типы данных и ограничения длины должны применяться для идентификатора карты, месяца, идентификатора операции и признака отправки?

### R-13: есть замечания

> Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.

- **F-9 [существенный] Полнота** (стр. 1, строка 41; модель): «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API».»  
  Проблема: В тексте указано чтение и сохранение настроек, однако в дочернем документе REST API описан только метод GET для сохранения с url /alerts/saveLimit, но нет метода для чтения настроек. Из-за этого разработчик не сможет реализовать чтение настроек через API.  
  Исправить: Добавить в дочерний документ описание метода REST API для чтения настроек или скорректировать формулировку, если чтение происходит иначе.  
  Вопрос: Каким именно методом API реализовано чтение настроек приложения?

### R-14: есть замечания

> заполняются тестировщиками

- **F-1 [критичный] Полнота** (стр. 1, строка 45; правило): «заполняются тестировщиками»  
  Проблема: Требование представляет собой незаполненную заглушку («заполняются тестировщиками»), не содержащую конкретных правил, сценариев или требований к тестированию. Разработчик и тестировщик не смогут понять, какие именно проверки здесь требуются.

  Исправить: Удалить заглушку или описать конкретные требования к тестовым сценариям и процедуре тестирования.  
  Вопрос: Какие конкретные требования к тестированию должны быть зафиксированы в этом разделе?

### R-18: есть замечания

> Description Сохранение порога. Функциональные требования: чтение порога

- **F-10 [существенный] Однозначность** (стр. 3, строка 112; модель): «Description Сохранение порога. Функциональные требования: чтение порога»

  Вопрос: Данный метод REST API предназначен для сохранения или для чтения порога?

## Приложение. Отклонённые замечания (прозрачность)

- Критик: «Перевести 500 ₸ | Счётчик показывает 19 900 ₸». В функциональном требовании Ф-2 указано: «Переводы и снятие наличных исключаются». В данном критерии приёмки описан перевод на 500 ₸ при исходных расходах 19 900 ₸, и ожидается, что счётчик останется 19 900 ₸. Однако термин «перевести» неоднозначен: если это перевод со счета/карты (расход), то он должен исключаться из расходов по правилу Ф-2, но тогда непонятно, почему проверяется именно этот кейс в таблице расходов. Если это входящий перевод, это не отражено явно. Причина: Замечание основано на неверной интерпретации: в критерии приемки указан перевод, который по правилу Ф-2 исключается из расходов, поэтому счетчик и остается неизменным. Основание: «Переводы и снятие наличных исключаются.» (стр. 1, строка 28).
- Критик: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR.». В требовании не указан HTTP-статус ответа для случая отклонения суммы, хотя в разделе ответов описаны коды 200, 400, 401, 403, 404, 500. Причина: Ложное замечание: в разделе статусов указаны все возможные коды ответа, включая 400 для ошибок валидации. Основание: «400. Ответ в случае, если параметры запроса заполнены неверно.» (стр. 3, строка 158).
- Критик: «200. Ответ в случае успешного выполнения метода.». В описании статуса 200 не указана структура ответа для успешного выполнения, хотя в примере ниже упоминается статус 201 и тело ответа с результатом сохранения. Причина: Это пожелание к детализации описания успешного ответа, при этом сам пример ответа с телом приведен ниже в спецификации.
- Критик: «При ошибке ввода сообщение появляется под полем.». В требовании не указан конкретный текст сообщения об ошибке для различных видов неверного ввода, а также стиль оформления текста (цвет, размер шрифта), что может привести к несогласованной реализации в UI. Причина: Требование детализировать конкретный текст и стили сообщения об ошибке является вкусовщиной и избыточной детализацией для ТЗ.

## Замечания агента вне эталона (кандидаты на пополнение эталона)

- F-1 [критичный] Полнота: Дочерний документ (часть B) описывает только сохранение порога (saveLimit), но не чтение настроек. Последовательность требует получение порога карты. Разработчик не найдет API для чтения.
- F-2 [критичный] Полнота: Строка таблицы слита в одну, неразборчиво разделены столбцы. Тестировщик не может выделить предусловия, действие и результат.
- F-12 [критичный] [Безопасность и персональные данные]: В документе отсутствуют требования к защите хранимых данных: шифрование, контроль доступа, маскирование, сроки хранения, аудит доступа, соответствие PCI DSS. Разработчик не будет знать, как защищать чувствительные данные карты и клиента, тестировщик не сможет проверить безопасность.
- F-13 [критичный] [Безопасность и персональные данные]: UI-описание не содержит требований к маскировке номера карты на экране. API использует cardId, но нет явного запрета передачи и логирования полного PAN. Разработчик может вывести полный номер карты в UI или логировать его.
- F-16 [существенный] Полнота: Процесс не отражает ограничение «максимум один push за календарный месяц» (Ф-3) и не показывает обработку возвратов, смены месяца, изменения порога. Разработчик может реализовать отправку push при каждом достижении порога.
- F-19 [существенный] Полнота: Неясно, как структурированы данные: одна таблица с дублированием порога и признака отправки на каждую операцию, или две таблицы (транзакции и месячные агрегаты). Признак отправки относится к месяцу, а не к операции. Разработчик может создать неверную схему.
- F-21 [существенный] Полнота: Шаг не описывает валидацию параметра enabled (должен быть 0 или 1) и не указывает, какой ошибку вернуть при недопустимом значении. В спец. правилах только про сумму, в параметрах запроса — enabled 0 или 1. Отсутствие обработки может привести к сохранению некорректного значения или 500-й ошибке.
- F-22 [существенный] Однозначность: Упоминается код 201, которого нет в списке статусов (метод GET, успешный только 200). Фраза «400, 401 и далее» неясна: не перечислены все коды ошибок (403, 404, 500), нет чёткого перечня.
- F-23 [существенный] Полнота: У параметра result нет условия возвращения (в отличие от amount — «При успехе», message — «При ошибке»). Примеры показывают result в успехе (OK) и в одной ошибке (ERROR), но в других ошибках (R-56, R-58, R-61, R-63) поле отсутствует. Разработчик не поймёт, всегда ли возвращать result.
- F-24 [существенный] Полнота: В разделе статусов нет строки для кода 404 (нет записи «404. ...»). Есть только это текстовое правило и пример R-61. Разработчик может упустить необходимость вернуть 404.
- F-25 [существенный] [Данные, единицы и типы]: Перечислены поля хранилища, но для каждого не указан источник (откуда приходит) и потребитель (кто читает). Например, «признак отправки» — кто устанавливает? Кто сбрасывает? Без этого разработчик не знает, заполнять ли поле при вставке, а тестировщик — как проверить.
- F-31 [существенный] [Область применения, термины и граничные значения]: Критерии приёмки не покрывают граничные значения порога: 1 000 ₸ и 1 000 000 ₸. Нет теста на покупку, которая сразу сильно превышает порог (например, расходы 0, порог 1 000, покупка 50 000). Нет проверки нулевых/отрицательных сумм покупок (хотя порог не может быть ≤0).
- F-32 [существенный] [Область применения, термины и граничные значения]: Термин «активная карта» не определён. Неясно, включает ли он карты с открытым счётом, но просроченные, или карты в процессе выпуска. От этого зависит, кому доступен функционал.
- F-33 [существенный] [Негативные и альтернативные сценарии]: Не описано поведение при сбое сервиса push: есть ли ретраи, dead-letter очередь, видит ли пользователь ошибку. Push — асинхронный канал, но требований к надежности доставки нет.
- F-34 [существенный] complete · Сценарий: Покупка в иной валюте (USD) на карте KZT: Не определено, включаются ли покупки в иностранной валюте в расходы по карте KZT и как конвертируется сумма. Разработчик может не добавить конвертацию, тестировщик не проверит.
- F-37 [существенный] Ранжированность: В спецификации отсутствует ранжирование требований по важности/стабильности (IEEE 830 4.3.7). Все требования выглядят равноправными.
- F-38 [существенный] Полнота набора: В части B (REST API) описан только эндпоинт сохранения лимита. API для отправки push-уведомления отсутствует, хотя последовательность его требует.
- F-39 [существенный] Полнота набора: Для Ф-4 нет ни одного критерия приёмки, проверяющего поведение при смене порога.
- F-41 [существенный] [Согласованность частей документа]: Формат ответа при успехе содержит поля result, amount, enabled. При ошибке 400 (валидация) возвращается {result:"ERROR", message}. При ошибках 401, 403, 404, 500 возвращается только {message}. Клиентское приложение не сможет единообразно обрабатывать ошибки. Разработчик реализует разные парсеры.
- F-42 [существенный] [Эксплуатация и управление требованиями]: Нефункциональное требование (SLA 1 минута) не сопровождается требованиями к мониторингу, метрикам и алертам. Разработчик не добавит замеры латентности, тестировщик не сможет проверить SLA в продакшене.

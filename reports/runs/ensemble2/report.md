## 3. Проверка каждого требования

### R-01: есть замечания

> Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.

- **F-18 [существенный] Однозначность** (стр. 1, строка 16; модель): «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»  
  Проблема: Фраза «узнать о достижении личного бюджета» не уточняет способ информирования (push‑уведомление, сообщение в UI и т.п.), поэтому возможны разные интерпретации.  
  Исправить: Уточнить способ информирования, например: «получать push‑уведомление о достижении личного бюджета в момент покупки».  
  Вопрос: Какой канал информирования предполагается использовать?

### R-02: есть замечания

> Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.

- **F-19 [существенный] Уместность уровня** (стр. 1, строка 18; модель): «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.»  
  Проблема: В требовании указаны конкретные компоненты реализации (сервис push), что относится к уровню проектных решений, а не к бизнес‑требованию.  
  Исправить: Переформулировать без детализации реализации: «мобильное приложение взаимодействует с сервисом уведомлений, а карточный процессинг передаёт данные о расходах».  
  Вопрос: Нужна ли детализация реализации push‑сервиса на уровне требований?

### R-03: есть замечания

> Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить». При ошибке ввода сообщение появляется под полем.

- **F-20 [существенный] Однозначность** (стр. 1, строка 20; модель): «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить». При ошибке ввода сообщение появляется под полем.»  
  Проблема: Не указано, какие именно ошибки ввода могут возникнуть и какой текст сообщения должен отображаться, что допускает разные трактовки.  
  Тот же дефект также здесь: стр. 1, строка 20 «При ошибке ввода»  
  Исправить: Перечислить возможные ошибки (например, «значение ниже минимального порога», «нечисловой ввод») и указать конкретный текст сообщения для каждой.  
  Вопрос: Какие конкретные сообщения об ошибке требуются?

### R-04: есть замечания

> Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.

- **F-21 [существенный] Полнота** (стр. 1, строка 24; модель): «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.»  
  Проблема: Не описаны действия системы в случае ошибки отправки push‑уведомления и не указаны граничные сценарии (например, повторные покупки в одном месяце).  
  Исправить: Добавить описание обработки ошибок (например, повторная попытка отправки, логирование) и уточнить поведение при нескольких достижениях порога в одном календарном месяце.  
  Вопрос: Как обрабатывается ошибка отправки push‑уведомления?

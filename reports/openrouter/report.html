Документ не готов к разработке и тестированию из-за 17 критических дефектов, делающих реализацию невозможной или гарантированно неверной. Основные блокеры: 1) API описан противоречиво и небезопасно: «HTTP-метод GET используется для операции сохранения порога (изменения состояния)» и «Логика метода (шаг 5) предписывает при ошибке валидации суммы вернуть 200 с result=ERROR, но в разделе Статусов для неверных параметров задан код 400». 2) Отсутствует API чтения настроек: «Дочерний документ (часть B) описывает только сохранение порога (saveLimit), но не чтение настроек». 3) Прямое противоречие бизнес-правил: «Ф-3 ограничивает один push в месяц, а Ф-4 разрешает новый push при смене порога в том же месяце — прямое противоречие». 4) Несогласованность единиц измерения: «Сумма покупки хранится в тийинах (1/100 тенге), а порог — в тенге... Разработчик может сравнивать напрямую, что даст ошибку в 100 раз». 5) Отсутствуют требования безопасности (PCI DSS, маскировка PAN, защита push). 6) Нет продакшн-URL, версии API, OpenAPI-схемы: «Отсутствует продакшн-URL (Prod: —), нет ссылки на Swagger/OpenAPI (Swagger —), не указана версия API». 7) Критерии приёмки противоречат требованиям по дате учёта покупки. Без устранения этих дефектов разработчик реализует неработоспособный и небезопасный функционал, а тестировщик не сможет составить тест-кейсы.

Исправить в первую очередь
  1. Исправить HTTP-метод сохранения порога с GET на POST/PUT и устранить противоречие кодов ответа (200+ERROR vs 400) в разделе «Контракт API».
  2. Добавить эндпоинт чтения настроек порога (GET) в Часть B.
  3. Разрешить противоречие Ф-3 и Ф-4: четко определить, отправляется ли push при смене порога в текущем месяце, если он ещё не уходил.
  4. Описать конвертацию единиц (тийины ↔ тенге) в правиле сравнения накопленных расходов с порогом (Ф-3).
  5. Добавить продакшн-URL, версию API и ссылку на OpenAPI/Swagger.
  6. Добавить требования безопасности: шифрование, маскировка PAN в UI/логах, состав push без чувствительных данных, PCI DSS, согласование с ИБ.
  7. Уточнить определение «проведённой покупки» и привязать критерии приёмки к дате авторизации/клиринга единообразно.
  8. Описать схему хранения: разделение транзакций и месячных агрегатов, источник/потребитель поля «признак отправки».
